# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

MangaVault is a Java 21 / Spring Boot 3.5 backend at the repository root plus a React (Vite) client under `frontend/`. The project is an online story-reading website built as a graduation internship project — `docs/HƯỚNG ĐI THỰC TẬP.md` is the authoritative requirements document.

The full feature set from the requirements doc (section 1.6, F01–F21) is implemented: Story/Chapter reading, JWT auth with GUEST/USER/ADMIN roles, genres, follows, reading history/resume, comments with reporting, star ratings, user administration, and dashboard statistics. `AGENTS.md` mentions PostgreSQL in the target architecture, but the application uses MySQL (the requirements doc, section 1.3.4, also specifies MySQL). Treat a database switch or moving the backend into `backend/` as an explicit migration, not an incidental cleanup.

The app is deployed: backend as a Docker image on Render, frontend as a static build on Vercel, database on Aiven MySQL (free tier — see `README.md` for live URLs and the required environment variables). `Dockerfile` builds a fat jar; `frontend/vercel.json` provides the SPA rewrite so client-side routes survive a hard refresh.

A `docker-compose.yml` at the root provides local MySQL (database `manga_vault`, user `manga_user`).

## Commands

Use the Maven wrapper so a system Maven installation is unnecessary.

```powershell
# Run the backend (default port 8080)
.\mvnw.cmd spring-boot:run

# Compile
.\mvnw.cmd compile

# Run all tests
.\mvnw.cmd test

# Run one test class
.\mvnw.cmd -Dtest=MangaVaultApplicationTests test

# Run one test method
.\mvnw.cmd -Dtest=MangaVaultApplicationTests#contextLoads test

# Build the executable package (includes tests)
.\mvnw.cmd package
```

On POSIX systems, replace `.\mvnw.cmd` with `./mvnw`.

There is currently no configured lint or formatting command.

Frontend (from `frontend/`):

```powershell
npm install       # install dependencies
npm run dev       # Vite dev server on port 5173
npm run build     # production build
```

### Local runtime configuration

The application requires Java 21 and a reachable MySQL database. Configure these environment variables before starting it:

```powershell
$env:DB_URL = "jdbc:mysql://localhost:3306/manga_vault"
$env:DB_USERNAME = "manga_user"
$env:DB_PASSWORD = "<local password>"
```

`DB_URL` and `DB_USERNAME` have the defaults shown above; `DB_PASSWORD` has no default. Hibernate currently uses `ddl-auto=update`, so application startup may modify the local schema. After startup, verify `GET http://localhost:8080/api/health`. The Postman collection in `postman/` covers the implemented endpoints.

Tests run against H2 in MySQL-compatibility mode (`src/test/resources/application-test.properties`, `@ActiveProfiles("test")`), not the dev MySQL instance — `mvnw test` works without Docker or a running database. `StoryApiIntegrationTest` covers the visibility/publish access rules and the authorization matrix via `MockMvc` + `@WithMockUser`; keep it in sync when changing `SecurityConfig` matchers.

## Architecture

The backend package root is `com.daniel.mangavault`. Requests follow the standard layered flow:

```text
HTTP client / future React app
  -> controller
  -> service
  -> repository (Spring Data JPA)
  -> MySQL
```

- `controller`: HTTP binding and `ApiResponse<T>` construction. Keep controllers thin; they must not call repositories directly or contain business logic.
- `service`: business flow, repository coordination, and currently entity/DTO mapping.
- `repository`: Spring Data JPA persistence interfaces.
- `entity`: internal JPA models. Do not expose these directly through controllers.
- `dto/request` and `dto/response`: public API input/output contracts.
- `exception`: application exceptions and centralized HTTP error translation.
- `config`: `AdminAccountInitializer` (bootstrap ADMIN account) and `DemoDataInitializer` (seeds sample stories when the catalogue is empty, toggled by `app.demo.seed`).
- `security`: `SecurityConfig` (JWT + CORS + authorization rules) and `CurrentUserProvider` (resolves the caller from the JWT `uid` claim — see below).
- `mapper`: still a placeholder; entity→DTO mapping stays inline in services until complexity justifies extracting it.

The story flow spans `StoryController`/`ChapterController` -> `StoryService`/`ChapterService` -> `StoryRepository`/`ChapterRepository` -> `Story`/`Chapter`. Services map entities to response DTOs. IDs are UUID strings generated by JPA, enum values are stored as strings, and timestamps are generated by Hibernate. `chapters` has a unique constraint on `(story_id, chapter_number)`. Creating a chapter also touches the parent story's `updatedAt` (same transaction) so `sort=updated` reflects new chapters — preserve this when changing chapter creation. Reading a chapter increments `stories.view_count` via a `@Modifying` bulk update (`StoryRepository.incrementViewCount`), deliberately bypassing `save()` so `@UpdateTimestamp` does not fire and reads don't reorder the "recently updated" sort. The same pattern applies to `updateRatingAggregate`.

`Story.visibility` is a real access boundary, not a display hint: every public-facing query (`searchPublic`, `getStoryById`, chapter listing, chapter read) filters to `PUBLIC` and a hidden story/chapter returns `STORY_NOT_FOUND`/`CHAPTER_NOT_FOUND` (404), never 403 — the goal is that a private story is indistinguishable from a nonexistent one. Admin has parallel endpoints (`AdminStoryController`, `AdminChapterController`) that see everything, because the public listing excludes what the admin needs to manage.

Six additional entities extend the domain, each with a repository, service and controller: `Genre` (many-to-many with `Story` via `story_genres`, deletion blocked while assigned), `Follow` and `ReadingProgress` (one row per user+story — `ReadingProgress` doubles as reading history and "resume" position), `Rating` (one row per user+story, denormalized onto `Story.ratingAvg`/`ratingCount`), `Comment` and `CommentReport` (report count denormalized onto `Comment.reportCount` for the moderation queue). `StoryService.deleteStory` cascades deletes across all of them before deleting the story itself — extend that method, in dependency order, whenever a new table references `stories`.

`CurrentUserProvider` (`security/`) resolves the authenticated user without a custom `UserDetailsService`: the JWT already carries a `uid` claim (see `AuthService.generateToken`), so `requireUserId()` reads it straight off `SecurityContextHolder`. `requireUser()` additionally loads the entity and rejects `UserStatus.BANNED` — this is the enforcement point for bans, since a JWT issued before a ban stays cryptographically valid until it expires.

All current endpoints are under `/api`. Full list with request/response shapes lives in `README.md` and `postman/MangaVault.postman_collection.json`; the shape to know when adding a new one:

```text
GET    /api/health, /api/genres, /api/stories/**, /api/chapters/**        (public)
GET    /api/stories/{id}/comments, /api/stories/{id}/rating               (public)
/api/me/**, follow, save progress, rate, post/edit/delete comment, report (authenticated)
/api/admin/**                                                             (ADMIN)
```

Matcher order in `SecurityConfig.authorizeHttpRequests` matters: user-scoped sub-paths under `/api/stories/**` (follow, rating PUT/DELETE, comment POST) are declared *before* the blanket `GET /api/stories/**` permitAll rule, or they would fall through as public.

Responses use the shared `ApiResponse<T>` envelope. Success responses use application code `1000`. Errors flow through `GlobalExceptionHandler`: `AppException` carries an `ErrorCode` enum entry that supplies both the HTTP status and the application code — see `exception/ErrorCode.java` for the full, grouped list (400/401/403/404/409 families). Validation and malformed-body errors return 400 with code `4000`; an invalid enum query/path parameter (e.g. `?status=bogus`) is caught by a `MethodArgumentTypeMismatchException` handler and also returns 400/4000 rather than 500. Add new error cases to `ErrorCode` rather than inventing ad-hoc codes. Paginated lists wrap items in `PageResponse<T>`. Preserve this envelope when extending the existing API unless intentionally changing the API contract.

Security (`security/SecurityConfig`): stateless JWT via Spring's OAuth2 resource server, HS256 with `app.jwt.secret` (env `JWT_SECRET`; dev default in properties — `AdminAccountInitializer` logs an ERROR at startup if this default, or the default `ADMIN_PASSWORD`, is still in effect). `AuthService` issues tokens with a `role` claim mapped to `ROLE_*` authorities and refuses to log in a `BANNED` account. 401/403 responses are written as `ApiResponse` JSON by the entry point/denied handler in `SecurityConfig`, not the `@RestControllerAdvice`. CORS also lives in `SecurityConfig` so preflights pass the filter chain; the allowed-methods list must include `PATCH` (used by publish-toggle and admin user status/role endpoints) or those requests die at the preflight. When signing JWTs with a symmetric key, `JwsHeader.with(MacAlgorithm.HS256)` must be passed to the encoder explicitly.

`stories.slug`, `users.username`, `users.email`, `genres.name`, `genres.slug` are unique (DB constraint + service-level check). Any new nullable/non-null column added to an existing table (`stories`, `chapters`, `users`) must declare a `columnDefinition` with `DEFAULT` — `ddl-auto=update` never backfills existing rows, so a bare `nullable=false` column breaks startup against a database that already has data.

Admin UI lives under `frontend/src/pages/admin/` with API calls split across `frontend/src/services/adminService.js` (stories/chapters), `genreService.js`, `userService.js`, `commentService.js` (also holds moderation + stats calls); user-facing personal features live in `libraryService.js` (follows, history, ratings). Route guards: `routes/RequireAdmin.jsx` (ADMIN only) and `routes/RequireAuth.jsx` (any signed-in user) both redirect to `/login`, backed by `context/AuthContext.jsx` (token in localStorage, attached by an axios interceptor in `services/api.js`) and `context/ThemeContext.jsx` (global light/dark, `body.dark` class). The frontend guard is UX only — authorization is enforced by the backend.

Known debt: OSIV is still enabled (lazy loading across several new associations — `Follow.story`, `ReadingProgress.chapter`, `Comment.user`, etc. — relies on it staying on); `spring.jpa.properties.hibernate.default_batch_fetch_size=20` mitigates the N+1 fan-out this would otherwise cause. The legacy `mangas` table may still exist in local databases. `Story.description`/`author` are plain `text`/`varchar` rather than the separate `authors` table the requirements doc's ER diagram implies — documented as a known simplification, not silently diverged from. Docker Desktop on the primary dev machine has been unreliable (daemon hangs) — the test suite runs on H2 specifically so development isn't blocked by it; if MySQL-specific behavior needs verifying, prefer the deployed Aiven instance over waiting on local Docker.

## Repository-specific conventions

- Use constructor injection, as in the current service/controller code.
- Validate input through request DTOs; keep generated fields such as IDs and timestamps out of creation requests.
- Centralize exception-to-response handling rather than adding controller-level error responses.
- API authorization must be enforced by the backend when security is implemented; frontend visibility is not an authorization boundary.
- Centralize future frontend API calls under `frontend/src/services`.
- Use transactions for operations that update multiple entities, define cascade behavior deliberately, and avoid N+1 query patterns as relationships are added.
- Check `README.md` for the project overview/current progress, `docs/LEARNING_LOG.md` for the learning-task history, `docs/PROJECT_SCOPE.md` for MVP scope and physical layout, and `AGENTS.md` for the broader target-domain constraints. When these describe planned architecture that conflicts with executable configuration, follow the current code/build files unless the task explicitly performs the migration.
