# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

MangaVault is a Java 21 / Spring Boot 3.5 backend at the repository root plus a React (Vite) client under `frontend/`. The project is an online story-reading website built as a graduation internship project — `docs/HƯỚNG ĐI THỰC TẬP.md` is the authoritative requirements document.

The implemented domain is Story + Chapter (public read APIs, search, pagination) with a working reader UI. Users/JWT/roles and admin CRUD are planned but not implemented yet. `AGENTS.md` mentions PostgreSQL in the target architecture, but the application uses MySQL (the requirements doc, section 1.3.4, also specifies MySQL). Treat a database switch or moving the backend into `backend/` as an explicit migration, not an incidental cleanup.

A `docker-compose.yml` at the root provides local MySQL (database `manga_vault`, user `manga_user`).

## Commands

Use the Maven wrapper so a system Maven installation is unnecessary.

```powershell
# Run the backend (default port 8080)
.\mvnw.cmd spring-boot:run

# Compile
.\mvnw.cmd compile

# Run all tests
.\mvnw.cmd test

# Run one test class
.\mvnw.cmd -Dtest=MangaVaultApplicationTests test

# Run one test method
.\mvnw.cmd -Dtest=MangaVaultApplicationTests#contextLoads test

# Build the executable package (includes tests)
.\mvnw.cmd package
```

On POSIX systems, replace `.\mvnw.cmd` with `./mvnw`.

There is currently no configured lint or formatting command.

Frontend (from `frontend/`):

```powershell
npm install       # install dependencies
npm run dev       # Vite dev server on port 5173
npm run build     # production build
```

### Local runtime configuration

The application requires Java 21 and a reachable MySQL database. Configure these environment variables before starting it:

```powershell
$env:DB_URL = "jdbc:mysql://localhost:3306/manga_vault"
$env:DB_USERNAME = "manga_user"
$env:DB_PASSWORD = "<local password>"
```

`DB_URL` and `DB_USERNAME` have the defaults shown above; `DB_PASSWORD` has no default. Hibernate currently uses `ddl-auto=update`, so application startup may modify the local schema. After startup, verify `GET http://localhost:8080/api/health`. The Postman collection in `postman/` covers the implemented endpoints.

The sole test is an `@SpringBootTest` context-load test and can therefore be affected by database configuration.

## Architecture

The backend package root is `com.daniel.mangavault`. Requests follow the standard layered flow:

```text
HTTP client / future React app
  -> controller
  -> service
  -> repository (Spring Data JPA)
  -> MySQL
```

- `controller`: HTTP binding and `ApiResponse<T>` construction. Keep controllers thin; they must not call repositories directly or contain business logic.
- `service`: business flow, repository coordination, and currently entity/DTO mapping.
- `repository`: Spring Data JPA persistence interfaces.
- `entity`: internal JPA models. Do not expose these directly through controllers.
- `dto/request` and `dto/response`: public API input/output contracts.
- `exception`: application exceptions and centralized HTTP error translation.
- `config`, `mapper`, and `security`: placeholder package boundaries; concrete implementations do not exist yet.

The story flow spans `StoryController`/`ChapterController` -> `StoryService`/`ChapterService` -> `StoryRepository`/`ChapterRepository` -> `Story`/`Chapter`. Services map entities to response DTOs; move this into `mapper` only when mapping complexity justifies it. IDs are UUID strings generated by JPA, enum values are stored as strings, and timestamps are generated by Hibernate. `chapters` has a unique constraint on `(story_id, chapter_number)`. Creating a chapter also touches the parent story's `updatedAt` (same transaction) so `sort=updated` reflects new chapters — preserve this when changing chapter creation.

All current endpoints are under `/api`:

```text
GET    /api/health                            (public)
GET    /api/stories?keyword=&status=&sort=&page=&size=
                                              (public; status = enum filter, sort = latest|updated)
GET    /api/stories/{id}                      (public)
GET    /api/stories/{id}/chapters             (public; summaries only — never chapter content)
GET    /api/chapters/{id}                     (public; full content + prev/next chapter ids)
POST   /api/auth/register                     (public; always creates role USER)
POST   /api/auth/login                        (public; returns JWT + username + role)
POST   /api/admin/stories                     (ADMIN)
PUT    /api/admin/stories/{id}                (ADMIN)
DELETE /api/admin/stories/{id}                (ADMIN; also deletes its chapters, transactional)
POST   /api/admin/stories/{id}/chapters       (ADMIN)
PUT    /api/admin/chapters/{id}               (ADMIN)
DELETE /api/admin/chapters/{id}               (ADMIN)
```

Responses use the shared `ApiResponse<T>` envelope. Success responses use application code `1000`. Errors flow through `GlobalExceptionHandler`: `AppException` carries an `ErrorCode` enum entry that supplies both the HTTP status and the application code (`4041`/`4042` not found — 404; `4090` slug, `4091` chapter number, `4092` username, `4093` email conflicts — 409; `4011` bad credentials, `4010` missing/invalid token — 401; `4030` insufficient role — 403); validation and malformed-body errors return 400 with code `4000`. Add new error cases to `ErrorCode` rather than inventing ad-hoc codes. Paginated lists wrap items in `PageResponse<T>`. Preserve this envelope when extending the existing API unless intentionally changing the API contract.

Security (`security/SecurityConfig`): stateless JWT via Spring's OAuth2 resource server, HS256 with `app.jwt.secret` (env `JWT_SECRET`; dev default in properties). `AuthService` issues tokens with a `role` claim mapped to `ROLE_*` authorities; 401/403 responses are written as `ApiResponse` JSON by the entry point/denied handler in `SecurityConfig`, not the `@RestControllerAdvice`. CORS also lives in `SecurityConfig` (the old `WebConfig` was removed) so preflights pass the filter chain. A bootstrap ADMIN account (`app.admin.*`, default admin/admin123) is created at startup when no ADMIN exists. When signing JWTs with a symmetric key, `JwsHeader.with(MacAlgorithm.HS256)` must be passed to the encoder explicitly.

`stories.slug`, `users.username`, and `users.email` are unique (DB constraint + service-level check). Admin UI lives under `frontend/src/pages/admin/` with API calls in `frontend/src/services/adminService.js`, guarded by `routes/RequireAdmin.jsx` + `context/AuthContext.jsx` (token in localStorage, attached by an axios interceptor in `services/api.js`). The frontend guard is UX only — authorization is enforced by the backend.

Known debt: OSIV is still enabled (lazy `chapter.getStory()` relies on it), the legacy `mangas` table may still exist in local databases, and the Postman collection is not yet updated to the Story/Chapter domain.

## Repository-specific conventions

- Use constructor injection, as in the current service/controller code.
- Validate input through request DTOs; keep generated fields such as IDs and timestamps out of creation requests.
- Centralize exception-to-response handling rather than adding controller-level error responses.
- API authorization must be enforced by the backend when security is implemented; frontend visibility is not an authorization boundary.
- Centralize future frontend API calls under `frontend/src/services`.
- Use transactions for operations that update multiple entities, define cascade behavior deliberately, and avoid N+1 query patterns as relationships are added.
- Check `README.md` for the project overview/current progress, `docs/LEARNING_LOG.md` for the learning-task history, `docs/PROJECT_SCOPE.md` for MVP scope and physical layout, and `AGENTS.md` for the broader target-domain constraints. When these describe planned architecture that conflicts with executable configuration, follow the current code/build files unless the task explicitly performs the migration.
